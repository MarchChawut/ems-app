# ฟีเจอร์ของระบบ (Feature Switches)

ระบบนี้แบ่งเป็น **ฟีเจอร์หลัก** (ปิดไม่ได้) และ **ฟีเจอร์เสริม** ที่ Super Admin เปิด/ปิดได้เองจากหน้า
`ตั้งค่า > ฟีเจอร์ของระบบ` — ออกแบบให้หน่วยงานอื่นนำไปติดตั้งแล้วเลือกใช้เฉพาะที่ต้องการ

## ฟีเจอร์

| ประเภท | ฟีเจอร์ | หมายเหตุ |
|---|---|---|
| หลัก (ปิดไม่ได้) | หน้าหลัก, พนักงาน, ข้อมูลส่วนตัว (เมนูรูปโปรไฟล์), ตั้งค่า, ความปลอดภัยของบัญชี | แท็บเริ่มต้นของระบบ |
| เสริม | การลา (ใบมาสาย / ใบออกก่อนเวลาเป็นตัวเลือกย่อย), ตารางเวร, หนังสือเข้า-ออก, แบบฟอร์ม, วัสดุ, ครุภัณฑ์, ติดตามงาน | เปิด/ปิดได้ |
| เสริม | แจ้งเตือนทาง LINE (เตือนงานตามเวลา / แจ้งขั้นตอนใบลา เป็นตัวเลือกย่อย) | ต้องตั้ง `LINE_*` ใน env |

## ใครเปิด/ปิดได้

**เฉพาะ `SUPER_ADMIN`** (ตรวจที่ server ใน `PATCH /api/feature-settings`; ADMIN ธรรมดาและสิทธิ์รายบุคคลไม่พอ)
ส่วนการอ่านสถานะ (`GET`) ทำได้ทุกคนที่ล็อกอิน เพราะเมนูต้องใช้ตัดสินว่าจะแสดงอะไร

## ปิดแล้วเกิดอะไรขึ้น ("ปิดจริง")

- เมนูซ้ายซ่อน และเข้าหน้านั้นตรงๆ ไม่ได้ (redirect ไปหน้าแรกที่ยังเปิดอยู่) — `requireFeaturePage()` ใน `page.tsx`
- API ของฟีเจอร์ตอบ **403 `FEATURE_DISABLED`** — ตรวจที่จุดเดียวใน `requireAuth()` (`src/lib/auth.ts`) จาก path ของ request
  จึงครอบทุก route ที่ใช้ `requireAuth`/`requirePermission` โดยไม่ต้องแก้ทีละไฟล์
- หน้าหลักข้ามการ์ด/วิดเจ็ตของฟีเจอร์ที่ปิด; cron เตือนงานและการแจ้งเตือนใบลาทาง LINE ข้ามเมื่อปิด
- **ข้อมูลไม่ถูกลบ** — เปิดกลับมาใช้ต่อได้

## ค่าเริ่มต้น

- **ระบบที่ใช้งานอยู่แล้ว:** ไม่มีแถวใน `feature_settings` = ทุกฟีเจอร์ **เปิด** (ไม่เปลี่ยนพฤติกรรมเดิมจนกว่า Super Admin จะแก้)
- **การติดตั้งใหม่:** `pnpm db:seed` จะปิดฟีเจอร์เสริมทั้งหมด (เหลือแท็บเริ่มต้น) เมื่อยังไม่มีผู้ใช้เลยและไม่เคยตั้งค่าฟีเจอร์ (ดู [GETTING-STARTED.md](./GETTING-STARTED.md))
  ตั้ง `SEED_ENABLE_ALL_FEATURES=true` เพื่อเปิดทั้งหมด (เดโม/CI)
- ค่า default ต่อฟีเจอร์ (เช่น เวลามาสาย 08:30, เวลาเริ่ม/เลิกงานของกฎการลาใหม่) แก้ได้ในการ์ดของฟีเจอร์นั้น

## เพิ่มฟีเจอร์ใหม่

1. เพิ่มบล็อกใน `FEATURES` ที่ `src/lib/features.ts` (id, หมวด, ชื่อ, คำอธิบาย, `pagePrefixes`, `apiPrefixes`, `dependents`, `options`, `config`)
   — การ์ดในหน้าตั้งค่า การตรวจ API/หน้า และการ validate ค่าจะตามเอง
2. เพิ่มเมนูใน `menuItems` ของ `DashboardShell.tsx` โดยใช้ **id เดียวกับฟีเจอร์** (มีเทสกันลืม)
3. เรียก `await requireFeaturePage('<id>', user.role)` ใน `page.tsx` ของหน้าใหม่
4. ถ้าฟีเจอร์มี cron/webhook ที่ไม่ผ่าน `requireAuth` ให้ตรวจ `getFeatureSettings()` ที่ต้น handler เอง
5. เพิ่มเคสในเทส `src/app/api/feature-guard.test.ts`

## ความปลอดภัย (สำหรับผู้พัฒนาต่อ)

- การเปิด/ปิดฟีเจอร์ **ไม่ใช่กลไกควบคุมสิทธิ์** — สิทธิ์ของผู้ใช้ยังตรวจแยกที่แต่ละ route (role / permission) เหมือนเดิมเสมอ
- การเทียบ path ใช้ `normalizeRequestPath()` (`src/lib/path-normalize.ts`) กันการหลบด้วย percent-encoding (`/api/%6Ceaves`),
  slash ซ้อน, `.`/`..`, ตัวพิมพ์ใหญ่-เล็ก, backslash; ฝั่ง allow-list (`isSetupAllowedPath`) ใช้แบบเข้มกว่า คือรับเฉพาะ path ที่สะอาดตรงเป๊ะ
- อ่านค่า flag จากฐานข้อมูลไม่ได้ → ถือว่า **เปิด (fail-open)** และ log error เพื่อไม่ให้ระบบทั้งหมดใช้ไม่ได้เพราะตาราง flag ผิดพลาด
  (ฟีเจอร์ที่ปิดไว้จะกลับมาเข้าถึงได้ชั่วคราวระหว่างนั้น แต่การตรวจสิทธิ์ของผู้ใช้ยังทำงานตามปกติ)
- มีแคชในหน่วยความจำ 5 วินาทีต่อ process; PATCH ล้างแคชของ process ที่รับคำขอทันที
- ทุกการเปลี่ยนแปลงถูก log (ผู้แก้, ค่าก่อน/หลัง); การปฏิเสธ (ไม่ใช่ Super Admin) ถูก log เป็น warning
